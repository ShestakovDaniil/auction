# Политика качества проекта — обязательна для любых изменений

1. Любое функциональное изменение (включая конфигурацию, роутеры, модели и миграции) проходит
   `make verify` **до** объединения в основную ветку.
2. Запрещены `pytest -k`/`-m` в составе `make verify` с отбором только удобных тестов,
   `|| true`, игнорирование кода возврата, `pytest.skip`, `xfail` для проблемных тестов,
   удаление тестов или искусственное исключение целевых модулей из coverage.
3. Порог — минимум **40% измеренного покрытия Python** с учётом ветвлений. Понижать нельзя.
   Показатель покрытия и отдельное требование покрыть ≥40% функций ТЗ — **разные метрики**;
   оба должны подтверждаться тестовой матрицей.
4. Нельзя ослаблять Ruff/Bandit, добавлять `# noqa`, `# nosec`, исключать файлы или целые
   классы предупреждений без документированной причины, примера ложного срабатывания,
   ревью и отдельного коммита. Тесты исключены из Bandit, поскольку сканируется
   эксплуатируемый код (`app`, `scripts`), а не тестовые данные.
5. Тесты MariaDB **должны** выполняться на отдельном `_test`-схеме. Код тестов удаляет
   таблицы, поэтому запуск без `TEST_DATABASE_URL` приводит к ошибке, а не к `skip`.
6. Для изменения бизнес-правила требуется тест успешного сценария, отрицательного сценария,
   граничного значения и, где применимо, проверки прав. Мутационная проверка `make mutation-check`
   должна обнаруживать подмену вычисления шага ставки.
7. Миграции не изменяют прежние ревизии после применения. Новые изменения оформляются новой
   ревизией; перед изменением схемы создаётся backup и проверяется сценарий обновления с данными.
8. Для `make restore` необходимо подтверждение точного имени БД; резервные копии, `.env` и
   отчёты не публикуются и не коммитятся.

В данном проекте исключения Ruff ограничены уже существующим профилем проверок E4, E7, E9, F;
его расширение/изменение согласовывается отдельно. Bandit вызывается с `-ll -ii`, то есть
блокирует находки **medium/high severity и medium/high confidence**: при работе со скриптами
резервирования, которые обоснованно используют `subprocess`, low-severity сигналы шумные.
Для production стоит расширять SAST-профиль, а не снижать его.
