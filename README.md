# Auction System
# Система учета и проведения аукционов (Auction API)

Веб-сервис для автоматизации проведения аукционов, управления лотами, фиксации ставок и учета продаж. Проект разработан в рамках сквозного практического курса.

---

## 🛠 Технологический стек

* **Язык программирования:** Python 3.11+ / Node.js / Go *(выбрать нужное)*
* **Фреймворк:** FastAPI / Express / Spring Boot *(выбрать нужное)*
* **База данных:** PostgreSQL / SQLite
* **Контроль версий:** Git

---

## Архитектура данных и Сущности

Система оперирует следующими ключевыми сущностями:
1. **Участники (Users/Sellers/Buyers):** Продавцы и покупатели системы.
2. **Лоты (Lots):** Товары, выставляемые на торги (содержат стартовую цену и описание).
3. **Аукционы (Auctions/Bids):** Сессии торгов и истории ставок с привязкой к лоту и покупателю.
4. **Продажи (Sales):** Итоговые транзакции по закрытым аукционам.

## Регламент ветвления и Git-Process

В проекте используется упрощенная модель **Git Flow**:

* **`main`** — стабильная ветка. Содержит только проверенный, протестированный и готовый к релизу код. Прямые коммиты в `main` **запрещены**. Релизы маркируются Git-тегами (например, `v0.1.0`).
* **`develop`** — основная ветка разработки. Сюда сливаются все реализованные фичи.
* **`feature/<название_фичи>`** — временные ветки для разработки конкретных задач (создаются от `develop` и сливаются обратно в `develop` через Merge Request / Pull Request).

### Правила внесения изменений и приемки (Code Review):
1. Запрещено делать `git push --force` в ветки `main` и `develop`.
2. Перед созданием Merge Request (MR) из фича-ветки в `develop`, разработчик обязан:
   * Проверить отсутствие конфликтов с `develop`.
   * Убедиться в корректности работы локального окружения.
3. Слияние в `develop` и `main` происходит только после проверки (Code Review) другими участниками команды.
